# 0003: Authentication and session model

- **Status:** accepted
- **Date:** 2026-11-10

## Context

v1's authentication was a critical failure: the JWT was signed client-side with a secret bundled to every visitor, the token lived in `localStorage`, and the server's auth middleware was a no-op — every API endpoint was unauthenticated (MASTER_PLAN §2.3 #1–2). v2 must not repeat any part of this.

## Decision

- Server-side sessions stored in Postgres (random 256-bit IDs, stored hashed), delivered as an `HttpOnly; Secure; SameSite=Lax` cookie with the `__Host-` prefix. No tokens in `localStorage`, ever.
- Passwords hashed with **Argon2id**; **WebAuthn passkeys** (`go-webauthn`) as the preferred factor, **TOTP** as fallback; optional OIDC (`go-oidc`) later.
- First-run setup wizard creates the single owner account; the API refuses to start in an "open"/no-owner state.
- RBAC roles `owner`, `admin`, `analyst`, `viewer`, plus an `approver` capability gating attack-run and remediation-apply actions, checked via one policy function and covered by generated authZ-matrix tests (every route × every role).
- Postgres Row-Level Security on `workspace_id` as defence in depth; the app connects as a non-superuser role.

## Rejected alternatives

- Client-signed JWTs (v1's approach) — root cause of the critical vuln; rejected outright.
- Token-in-localStorage sessions — vulnerable to XSS exfiltration; rejected in favour of httpOnly cookies.
